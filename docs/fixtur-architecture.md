## 1. What it is

Factur is a **B2B sales-engagement platform**. It connects a customer's
mailboxes (Gmail, Outlook/M365, plain SMTP/IMAP, SendGrid), sends sequenced
outbound campaigns to prospects, captures every reply and delivery event, runs
each contact through a state machine that decides what happens next, enriches
contact and account data from ZoomInfo, and syncs the whole picture back to
Salesforce.

Architecturally it is **one application built as ~60 running services**. They
are almost entirely decoupled and talk over **RabbitMQ**, not HTTP.
**Understanding the queue topology *is* understanding the system.**

```
 EXTERNAL                     PLATFORM                      EXTERNAL
 Gmail        ──▶┌────────────────────────────────────┐
 Outlook/M365 ──▶│ 2. INBOUND CAPTURE                 │
 SMTP / IMAP  ──▶│    listeners → enrichment          │
 SendGrid     ──▶│    ⇣ email_status_to_sort          │
                 │                                    │
 Web UI      ◀──▶│ 3. SORTING & STATE MACHINES        │
 (Angular)       │    email_sorter → xstate machines  │
                 │    ⇣ state_out / scheduler_queue   │
                 │                                    │──▶ Gmail
                 │ 4. OUTBOUND SEND PIPELINE          │──▶ Outlook/M365
                 │    scheduler → processor → senders │──▶ SMTP
                 │                                    │
                 │ 5. CONTACTS / ACCOUNTS / IMPORT    │
                 │    main_api_backend_v1 (monolith)  │
                 │                                    │
 1. IDENTITY  ──▶│ 6. CRM & ENRICHMENT SYNC           │◀──▶ Salesforce
 accounts /      │                                    │◀──  ZoomInfo
 clients /       │ 7. AI SERVICES (Gemini + PyTorch)  │
 SpiceDB         │ 8. PLATFORM: logging, stats, cron  │
                 └────────────────────────────────────┘
        MySQL · MongoDB · Redis · OpenSearch · S3 · SpiceDB
```

## 2. Technology mix

There is no single stack. Four coexist, roughly by generation and by job:

| Stack | Where |
|---|---|
| **Node.js / Express** (JS) | The original generation — `main_api_backend_v1`, the whole `*_i_v1` family, schedulers and processors |
| **NestJS** (TypeScript) | The newer generation — `automatic_scheduler_service`, `opportunity_service`, `salesforce_exporter`, `csv_export`, `ai_integration_api`, `main_api_listener` |
| **.NET / C#** | Mailbox-protocol work — `account_service`, all Outlook and SMTP listeners and senders, `email_events_receiver` |
| **Python** | ML inference (`facture_ai_email_processing`, PyTorch + Transformers) and mailbox unblocking |
| **Angular** | `main_frontend_v1` (**Angular 13**, NGXS, Bootstrap, Quill, ~456 files), `main_front_rework` (NgRx, Angular Material, Amplify), `PublicDatabaseFrontend` |

### Data stores

| Store | Holds | Why it matters |
|---|---|---|
| **MySQL** (Aurora) | Accounts, mailboxes, sequences, scheduling, email events — the transactional core | Database-per-service pattern |
| **MongoDB** (DocumentDB) | Contacts, accounts, lists, tasks, imports | Variable-shape records where customers define their own fields |
| **Redis** | Caching, rate limiting, per-mailbox cursors, de-duplication | |
| **OpenSearch** | Contact and account search indexes | `search-api` |
| **S3** | Import files, CSV exports, attachments | |
| **SpiceDB** | Authorization relationships | See §3 |

**A contact's full picture spans two databases** — the contact in MongoDB, its
sequence state in MySQL. `cdc-listener` tails MongoDB change streams to keep
downstream systems in step.

### Deployment

AWS **Elastic Beanstalk** (built by CodeBuild, images in ECR), fronted by
ALB/NLB. Environments are named `factur-<env>-<service>`. RabbitMQ is
**AmazonMQ**; MySQL is **Aurora**; MongoDB is **DocumentDB**. `infra_cdk`
(TypeScript CDK) is the authoritative AWS definition — `infra_terraform` is a
README-only stub. `facture_system_main` holds layered `docker-compose` files for
local dev plus the committed RabbitMQ `definitions.json` that documents the full
queue topology.

Metrics come out of nearly every service via `prom-client`; logs ship to a
Grafana / Loki / Promtail stack on EC2.

## 3. Identity and authorization

`account_service` (.NET) owns the **mailbox registry** and fans each mailbox out
to the right listener over the `accounts_subsystem` exchange.

> **If a mailbox never reaches a listener, that customer simply goes quiet — no
> error surfaces in the send pipeline.** This is the single most important
> failure mode to know about.

```
account_service ──▶ gmail_accounts   ──▶ gmail_event_listener
                ──▶ outlook_accounts ──▶ outlook_event_listener
                                     ──▶ outlook_accounts_sender ──▶ outlook_email_sender_service
                ──▶ smtp_accounts    ──▶ smtp_event_listener
                                     ──▶ smtp_accounts_sender ──▶ smtp_email_sender_service
                ──▶ accounts         ──▶ main_api_listener

listeners/senders report health back:  accounts_feedback_status ──▶ account_service
```

The `accounts` queue is bound with **all four routing keys**, so it gets a copy
of every mailbox event regardless of provider.

**Authorization is SpiceDB** — Zanzibar-style relationship tuples, not roles in
the application database. `account_service` writes the relationships,
`main_api_sidecart` answers permission checks for the API, `ai_integration_api`
checks against it too. `spice_schema_data_migration` **must run before SpiceDB
starts**; it applies the schema to the backing MySQL database.

Authentication still involves **AWS Cognito** (`auth-function`,
`lambda-cognito-event` as Lambda triggers), with `security-service` alongside.

**Mailbox unblocking:** Microsoft restricts a mailbox that trips its outbound
limits. `outlook_event_listener` detects it and emits `email_status_alerts`;
`restricted_user_unblocker_main_service` (Python) drives the unblock against the
Exchange admin API using certificate-based app auth.

## 4. Inbound capture

Four provider pipelines, all the same two-stage shape, all converging on **one**
queue: `email_status_to_sort`.

```
┌──────────┐  raw message ref  ┌────────────┐  normalised event
│ LISTENER │ ────────────────▶ │ ENRICHMENT │ ────────────────▶ email_status_to_sort
└──────────┘                   └────────────┘
polls the provider,            fetches body, parses headers,
decides what's interesting     threads, replies, matches to a contact
```

| Provider | Listener | Handoff | Enrichment | Stack |
|---|---|---|---|---|
| Gmail | `gmail_event_listener` | `gmail_processor` | `gmail_enrichment` | TypeScript |
| Outlook / M365 | `outlook_event_listener` | `outlook_processor` | `outlook_enrichment` | .NET |
| SMTP / IMAP | `smtp_event_listener` | `smtp_processor` | `smtp_enrichment` (older: `mts_enrichment`) | .NET |
| SendGrid | `sendgrid_webhook_i_v1` / `sendgrid_importer` | `email_events` | `sendgrid_enrichment` | Node |

Gmail is the most developed and the only one with dead-letter queues wired up.
Its listener runs on a **2-minute cron** and splits work per mailbox
(`gmail_listener_fetch_messages_per_user`) so one slow mailbox cannot block the
rest.

**`gmail_processor_event_not_matched`** is the queue worth knowing: mail that
arrived in a connected mailbox but could not be tied to a known contact or
sequence. Separate consumer, so unmatched mail never blocks the main path.

## 5. Sorting and state machines — the brain

**Sorting** answers *"what kind of message is this?"* — genuine reply,
out-of-office, bounce, unsubscribe, delivery receipt. **State machines** answer
*"so what happens to this contact?"* — advance a step, stop the sequence, mark
interested, create an opportunity.

```
email_status_to_sort ──▶ email_sorter ──┬──▶ email_status ──▶ task_service ──▶ sf_exporter ──▶ Salesforce
                                        ├──▶ state_in ──▶ ┌──────────────────┐
                                        │                 │  STATE MACHINES  │ (xstate)
                                        │                 └──────────────────┘
                                        │                        │ state_out
                                        │                        ▼
                                        │        state_machine_processing_i_v1
                                        │           │      │        │        │
                                        │    scheduler_q  email_status  list_service  activity-log
                                        └──▶ create_event_emails ──▶ statistics_service
```

All the machines are built on **xstate**. There are several because different
event sources enter through different queues:

| Service | Entry queue | Role |
|---|---|---|
| `state_machines` | `state_in_alt` | Newest generation |
| `state_machine_service_i_v1` | `state_in` | The long-standing main machine |
| `email_response_state_machine` | `state_in_email_status` | Reply classification outcomes |
| `sequence_state_machine` | `state_in_sequence` | Sequence-level, not contact-level |
| `state_machine_processing_i_v1` | `state_out` | Executes the side effects |
| `state-machine-processing-send-email` | `state_out_send_email` | Turns "send next" into a job |

### The one design idea to internalise

**Decision and effect are deliberately split.** A machine consumes `state_in*`,
computes the transition, emits `state_out*` describing *what was decided*. A
separate service consumes `state_out*` and performs the effects.

> **If effects are not happening but state is advancing, the fault is in a
> `state_out` consumer, not in the machine.**

This is also the most intricate part of the platform: five entry queues
(`state_in`, `state_in_alt`, `state_in_sequence`, `state_in_email_status`,
`state_in_email_response`) consumed by services with overlapping
responsibilities, and `state_in` bound to **both** `factur_exchange` and
`email_subsystem`. Trace the specific queue end to end before changing routing.

## 6. Outbound send

```
scheduler_queue ──▶ email_scheduler_service_i_v1   WHO gets WHAT and WHEN
                    (sending windows, timezones, mailbox capacity, stuck retries)
                         │ state_in → machine → state_out_send_email
                         ▼
                    state-machine-processing-send-email
                         │ email_to_process
                         ▼
                    email_processor_service_i_v1    renders the template:
                                                    merge fields, tracking links,
                                                    unsubscribe, threading headers
                         │ routes by the mailbox's provider
        ┌────────────────┼─────────────────────┐
   email_to_esp   email_to_esp_outlook   email_to_smtp
        │                │                     │
  email_sender_    outlook_email_        smtp_email_
  service_i_v1     sender_service        sender_service
   (Gmail API)      (MS Graph)             (SMTP)
        └────────────────┴─────────────────────┘
                         ▼  email_status + state_out → back to the machines
```

**Three senders, not one with branches**, because each provider differs in auth,
rate limits and threading: Gmail (OAuth, `threadId`, daily caps), Outlook (MSAL
against Graph, can be restricted outright by Microsoft), SMTP (no API-level
delivery feedback — events come back via the SMTP listener instead).

`email_scheduler_service_i_v1` is the **busiest service in the platform**. It
keeps bulk maintenance off the per-contact path with seven dedicated queues:
mailbox capacity rebalance, retry stuck contacts, schedule-on-delivered,
sequence edited / paused / archived, and bulk thread updates. It also runs its
own crons at roughly 2, 5, 15, 25 and 35 minutes plus a daily 04:00 sweep.

## 7. Contacts, accounts and data management

`main_api_backend_v1` is the API the web frontends talk to and by a wide margin
the largest component: **~340 source files, and the only service that touches
every data store** (MySQL, MongoDB, Redis, OpenSearch, S3, SpiceDB).

It does little heavy lifting itself. Its dominant pattern is: validate, write the
record, **publish a job**, return.

| It publishes… | …this picks it up |
|---|---|
| `import_queue` | `contact_import_service_i_v1` |
| `export_queue` | `csv_export` |
| `list_service` | `contact_add_llist_service_i_v1` |
| `contacts_addtosequence` | `add_sequence_service_i_v1` |
| `scheduler_queue` | `email_scheduler_service_i_v1` |
| `state_in` | the state machines |
| `activity-log`, `activity-log-sequence` | `activity_log_service_i_v1` |

**Contact import** is the heaviest bulk operation, split across three queues so
chunks stay independent and restartable:

```
CSV/API upload → S3 → import_queue → contact_import_service_i_v1  (split into chunks)
                    → import_chunk_queue → contact_import_service_i_v1  (chunks in parallel)
                    → import_process_queue → import_contact_account_validation_i_v1
                         validate + dedupe, domain parsing (psl), match to an account,
                         decide create vs update → state_in (start sequences) + activity-log
```

**One request–reply flow exists** in an otherwise fire-and-forget system:
`automatic_scheduler_service` asks `contact-service` to resolve a saved search
(`contact_service.resolve_save_search_by_id` → `automatic_scheduler_service.handle_contacts`),
then enrols the results. Note the `<target_service>.<action>` naming — the newer
convention, unlike the flat queue names everywhere else.

## 8. Salesforce and ZoomInfo

**Inbound:** `salesforce-importer` pulls via jsforce and stages to S3 →
`salesforce_importer_processing` (cron every minute) transforms and dedupes →
`inbound_tasks`, `ais_inbound_tasks` (to AI), and `sf_datasync`.

**Outbound:** three independent producers converge on one consumer.

```
cdc-listener          (MongoDB change streams)  ──┐
task_service          (engagement → SF task)    ──┤──▶ sf_exporter ──▶ salesforce_exporter ──▶ Salesforce
salesforse-datasync   (reconciliation, every 5s)──┘
```

Two design choices with consequences:

- **CDC instead of dual writes.** `cdc-listener` tails MongoDB change streams
  rather than making every writer notify Salesforce. Any service can edit a
  contact and the push happens automatically — **which also means an unintended
  write propagates straight into the customer's CRM.**
- **`sf_exporter` is a convergence point** for three producers with very
  different cadences. **If Salesforce writes look duplicated, look here first.**

**ZoomInfo:** the `zoominfo` service (auth via AWS Secrets Manager) enriches
contacts in place, imports net-new accounts, and participates in
`state_in`/`state_out` — enrichment is modelled as a state transition.
`zoominfo_datasync` does bulk reconciliation.

## 9. AI services

Two generations sitting side by side:

| | Self-hosted classification | Hosted generative |
|---|---|---|
| Services | `facture_ai_ingestion` + `facture_ai_email_processing` | `ai_integration_api` |
| Model | Local PyTorch / HuggingFace, **checked into the repo** | Google Gemini via `@google/genai` |
| Interface | RabbitMQ, async | HTTP (NestJS + Swagger) |
| Purpose | Classify replies at volume: interested / not interested / OOO / referral | Interactive AI product features |
| Vintage | 2023 | 2026 |

```
task_service ──┐
salesforce_importer_processing ──┤──▶ ais_inbound_tasks  (exchange: ai_subsytem)
                                 ▼
              facture_ai_ingestion (cron every minute; loads the task from MongoDB)
                                 │ ais_inference
                                 ▼
              facture_ai_email_processing (Python, PyTorch)
                                 │ ais_inference_status
                                 ▼
                     result written back onto the task
```

**The AI verdict does not act on its own.** It is written onto the task and
re-enters through `state_in`, so it is treated as just another input to the same
decision engine that handles a human-classified reply — which keeps the AI path
from needing a parallel set of business rules.

`ai_integration_api` is the newest component and structurally different: NestJS,
Swagger, JWT/Passport, SpiceDB permission checks, TypeORM on MySQL, `p-queue` to
throttle Gemini calls, `sanitize-html` to clean email before it reaches the model.

⚠️ `ais_gmail` and `ais_task_status` are declared in the broker but have **no
consumer in any repository** on its current branch. Confirm before relying on
either.

## 10. Messaging and reliability

RabbitMQ (AmazonMQ) is the backbone. All exchanges are **direct**, and the
near-universal convention is **routing key = destination queue name**.

Main exchanges: `factur_exchange` (the main bus) and `factur_exchange_dlx` (its
dead-letter exchange), plus `accounts_subsystem`, `clients_subsystem`,
`gmail_listener_subsystem`, `outlook_subsystem`, `smtp_subsystem`,
`email_subsystem`, `email_status`, `state_machine_subsystem`, `ai_subsytem`,
`sf_import` / `sf_export`.

### ⚠️ Misspelled exchange names are live and load-bearing

Several exchanges exist in **both** a correct and a misspelled form, and **both
are live in the broker**. Different services bind to different spellings.

| Correct | Misspelled | Notes |
|---|---|---|
| `email_subsystem` | `email_subsytem` | `sendgrid_importer`, `sendgrid_enrichment`, `gmail_enrichment_v1` use the misspelling; `email_sorter` and `sendgrid_enrichment_i_v1` use the correct one |
| `state_machine_subsystem` | `state_machine_subsytem` | |
| — | `ai_subsytem` | Misspelling only, but **consistent everywhere**, so it works |

**This is a real source of "the message vanished" bugs.** Check the spelling
before concluding a message was lost, and never "correct" one service alone.

Also: `sf_exporter` is used as both a queue name *and* an exchange name (in
`cdc-listener` and `salesforce_exporter`), alongside the real `sf_export`
exchange. And the repo itself is spelled `salesforse-datasync`.

### messaging-lib is where reliability lives

`@facturgit/messaging-lib` is the RabbitMQ client newer services build on:

- **Retry with dead-lettering** — a failure goes to `<queue>_retry` with a TTL,
  back to the main queue, then to `<queue>_dlq` after `RABBIT_MAX_RETRIES`.
- **Consistent-hash exchanges** — `publishToConsistentHashExchange` routes by
  group ID, so all messages for one mailbox or contact land on the same consumer
  and stay in order, while still scaling out.
- **Graceful shutdown** — channels drained on shutdown (default 10s) so in-flight
  messages survive a redeploy.
- **Automatic reconnection** via `amqp-connection-manager`.

> **The `*_i_v1` family predates this library and each hand-rolls its own AMQP
> client with none of the above. That is the single biggest reliability
> difference between the old and new generations of service.**

## 11. Things to be careful about

Straight from Factur's own code sweep:

- **Duplicated service generations run side by side**, and it is not obvious
  from the code which is authoritative in production: `state_machines` vs
  `state_machine_service_i_v1`, `email_sorter` vs `email_event_sorter_i_v1`,
  `sendgrid_enrichment` vs `sendgrid_enrichment_i_v1`, `smtp_enrichment` vs
  `mts_enrichment`, `gmail_enrichment` vs `gmail_enrichment_v1`, `csv_export` vs
  `contact_export_service_i_v1`, `cron_service_i_v1` vs
  `data_cleanup_cron_service`.
- **`cron_service_i_v1` and `data_cleanup_cron_service` are near-identical
  forks** — both report `name: facture_cron` and share ~100 source files. A
  change to one is easy to forget in the other.
- **Two API generations coexist:** `main_api_backend_v1` (the Express monolith)
  and `main_api_rework` (a NestJS rewrite), with `main_api_sidecart` doing
  authorization alongside.
- **`state_out_send_email` vs `state_out_send_email_new`** — `factur_exchange`
  binds both routing keys to the same queue. A migration artefact, not two paths.
- **Credential hygiene.** Several repositories contain committed `.env` files
  with a **live message-broker connection string including its password**.
  Factur's own page flags these for rotation into AWS Secrets Manager, which
  parts of the platform already use.

## 12. Security: act on this

Separate from the committed `.env` files above, the Confluence page titled
**"Accounts" (page id 5701646)** opens with *"DO NOT SHARE THIS PAGE WITH
ANYONE"* and then lists **live usernames and passwords in plaintext** — Apollo,
the Fixtur dev app at `app.fixtur.io`, Swagger, and several application users.

Not reproduced here, and should not be copied anywhere else.

1. **Rotate every credential on that page.** Anyone with read access to the
   space has had them, and page history keeps old versions after an edit.
2. **Delete the page including its version history**, not just its contents.
3. Move them to AWS Secrets Manager / SSM Parameter Store.
4. Audit who has access to the `Services` space.
5. Separately, sweep the repos for the committed `.env` files and rotate the
   broker password.

## What the old pages get wrong

The 2023-era pages in this space describe a much smaller system and contradict
the current architecture. If you read them, discount these:

| Old pages say | Actually |
|---|---|
| Authorization is **OPA / Rego** (plus an undecided Permify spike) | **SpiceDB**, Zanzibar-style relationship tuples |
| A Cognito user group *is* the organization; profile fields are `custom:` attributes | Cognito is still in the auth path via Lambda triggers, but tenancy and permissions live in `client_service` / `account_service` / SpiceDB |
| MySQL Aurora + MongoDB | Also Redis, OpenSearch, S3, SpiceDB — six stores |
| Gmail and SendGrid only | Four inbound pipelines: **Outlook/M365 and SMTP/IMAP too** |
| Angular 16 / 15.2.9 | **Angular 13** on `main_frontend_v1` |
| Node/Express + a little Python | Node, **NestJS, .NET/C#**, Python |
| One AI step doing sentiment analysis, logs stuck in the task doc | Two generations — a local PyTorch classifier and a Gemini-backed NestJS API |
| Salesforce import only | **Two-way** sync, plus ZoomInfo enrichment |

The old pages are still the only source for some UI-level detail (the user list,
add/edit user, mailbox ownership rules, country reference data), and their
documentation-standard page (`Templates and examples`) is worth reading before
writing anything new in the space. Their typos are load-bearing: `email_subsytem`
is a real exchange name; also "Sengrid", "Subsytem", "Frontent".

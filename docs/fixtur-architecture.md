# Fixtur — how the build actually works

Read from the Confluence `Services` space on 2026-09-09: **all 283 pages**, of
which ~40 are empty per-service templates and a dozen are generic
software-engineering theory copied from softwaretestingfundamentals.com.

The backbone is Factur's own nine-page `Factur Platform — System Architecture
Overview` series, generated by static analysis of all **97 repositories** in the
`FacturGit` GitHub organisation on their `development` branches. That makes it
unusually trustworthy — but it describes **what services are wired to do, not
what is deployed or taking traffic.** Where it and the operational pages
disagree, this file says so.

**Watch the dates.** The space contains three distinct eras and they contradict
each other. Roughly: pages under id 14,000,000 are 2023 design documents and are
largely superseded; the 22M–250M range is operational reality; the 340M–420M
range is the current architecture and user documentation.

---

## 1. What it is

Fixtur is a **B2B sales-engagement platform**, sold as SaaS and also used
internally by Factur. It connects a customer's mailboxes (Gmail, Outlook/M365,
plain SMTP/IMAP, SendGrid), sends sequenced outbound campaigns to prospects,
captures every reply and delivery event, runs each contact through a state
machine that decides what happens next, enriches contact and account data from
ZoomInfo, and syncs the picture back to Salesforce.

Live at `app.fixtur.io`. Its own docs describe it as a lightweight CRM/ERP for
prospecting.

Architecturally it is **one application built as ~60 running services**, almost
entirely decoupled, talking over **RabbitMQ** rather than HTTP.
**Understanding the queue topology *is* understanding the system.**

```
 EXTERNAL                     PLATFORM                      EXTERNAL
 Gmail        ──▶┌────────────────────────────────────┐
 Outlook/M365 ──▶│ 2. INBOUND CAPTURE                 │
 SMTP / IMAP  ──▶│    listeners → enrichment          │
 SendGrid     ──▶│    ⇣ email_status_to_sort          │
                 │                                    │
 Web UI      ◀──▶│ 3. SORTING & STATE MACHINES        │
 (Angular)       │    email_sorter → xstate machines  │
                 │    ⇣ state_out / scheduler_queue   │
                 │                                    │──▶ Gmail
                 │ 4. OUTBOUND SEND PIPELINE          │──▶ Outlook/M365
                 │    scheduler → processor → senders │──▶ SMTP
                 │                                    │
                 │ 5. CONTACTS / ACCOUNTS / IMPORT    │
                 │    main_api_backend_v1 (monolith)  │
                 │                                    │
 1. IDENTITY  ──▶│ 6. CRM & ENRICHMENT SYNC           │◀──▶ Salesforce
 accounts /      │                                    │◀──  ZoomInfo
 clients /       │ 7. AI SERVICES (Gemini + PyTorch)  │
 SpiceDB         │ 8. PLATFORM: logging, stats, cron  │
                 └────────────────────────────────────┘
        MySQL · MongoDB · Redis · OpenSearch · S3 · SpiceDB
```

## 2. Technology mix

No single stack. Four coexist, by generation and by job:

| Stack | Where |
|---|---|
| **Node.js / Express** (JS) | The original generation — `main_api_backend_v1`, the whole `*_i_v1` family, schedulers and processors |
| **NestJS** (TypeScript) | The newer generation — `automatic_scheduler_service`, `opportunity_service`, `salesforce_exporter`, `csv_export`, `ai_integration_api`, `main_api_listener`, `deliverability_service` |
| **.NET / C#** | Mailbox-protocol work — `account_service`, all Outlook and SMTP listeners and senders, `email_events_receiver` |
| **Python** | ML inference (`facture_ai_email_processing`, PyTorch + Transformers) and mailbox unblocking |
| **Angular** | `main_frontend_v1` (**Angular 13**, NGXS, Bootstrap, Quill, ~456 files), `main_front_rework` (NgRx, Angular Material, Amplify), `PublicDatabaseFrontend` (Angular 19 SSR) |

### Data stores

| Store | Holds |
|---|---|
| **MySQL** (Aurora) | Accounts, mailboxes, sequences, scheduling, email events — the transactional core, database-per-service |
| **MongoDB** (DocumentDB) | Contacts, accounts, lists, tasks, imports — variable-shape records with customer-defined fields |
| **Redis** | Caching, rate limiting, per-mailbox cursors, de-duplication |
| **OpenSearch** | Contact and account search indexes |
| **S3** | Import files, CSV exports, attachments, config, Loki log archive |
| **SpiceDB** | Authorization relationships |

**A contact's full picture spans two databases** — the contact in MongoDB, its
sequence state in MySQL. `cdc-listener` tails MongoDB change streams to keep
downstream systems in step.

### Deployment

AWS **Elastic Beanstalk** (CodeBuild → ECR), behind ALB/NLB. Environments named
`factur-<env>-<service>`. RabbitMQ is **AmazonMQ**; MySQL is **Aurora**; MongoDB
is **DocumentDB**. `infra_cdk` (TypeScript CDK) is authoritative — split into
nested stacks to stay under CloudFormation's 500-resource limit;
`infra_terraform` is a README-only stub. `facture_system_main` holds layered
`docker-compose` files for local dev plus the committed RabbitMQ
`definitions.json` documenting the full queue topology.

Metrics via `prom-client`; logs to a **Grafana / Loki / Promtail** stack on EC2,
archived to S3 with 14-day retention. Bastion host for admin access; **Pritunl
OpenVPN** for the team.

## 3. Identity and authorization

**This has been rebuilt, and the 2023 docs are wrong about it.** Those pages
describe AWS Cognito as the whole identity story, with a Cognito user group
*being* the organization. That is superseded.

Today:

- **`account_service` (.NET) issues JWTs.** A user logs in, `account_service`
  checks the hashed password in its own database and returns a JWT. A gateway /
  Lambda authorizer validates it. Cognito survives only as Lambda triggers
  (`auth-function`, `lambda-cognito-event`).
- **The JWT carries the tenancy and entitlement.** Claims: `nameid`, `email`,
  `role` (Admin/User), `clientid`, plus `package` and `permissions`.
- **`clientid` is multi-tenancy.** Middleware pulls it off the token, exchanges
  the UUID for a MongoDB client `_id`, and attaches it to every request. Mongo
  documents carry a `clientIds` **array**; MySQL a singular string. Users on the
  privileged `factur` / `superadmin` packages can override it from the query or
  body on GET/PUT/PATCH/DELETE — POST always takes it from the token.
- **Authorization is SpiceDB** (Zanzibar-style relationship tuples), *not*
  OPA/Rego and not the Permify spike the old docs left undecided. Middleware
  builds a permission string from `METHOD + PATH + PACKAGE + ROLE` and asks
  SpiceDB. Every route must exist in `spice_schema_data_migration`'s
  `permissions.csv` **exactly as written in the router**, or the check fails.
  `spice_schema_data_migration` must run *before* SpiceDB starts.

### Packages and roles

Access is gated first by **package**, then by **role**.

| Package | What it adds |
|---|---|
| Free | Read-only: contacts, accounts, opportunities, sequences, users, analytics |
| Basic | Create sequences (100/mo), add contacts (10k/mo), link mailboxes (10 users / 20 mailboxes), 100k contacts, 50k accounts, 1k opportunities |
| Advanced | Link **admin accounts**, global analytics |
| Premium | (not documented) |
| `factur` / `superadmin` | Internal; can override `clientId` |

Roles are just **Admin** and **User**. Each client is provisioned with one admin
who creates the rest.

### Mailbox fan-out — the top failure mode

`account_service` owns the mailbox registry and fans each mailbox out to the
right listener over `accounts_subsystem`.

```
account_service ──▶ gmail_accounts   ──▶ gmail_event_listener
                ──▶ outlook_accounts ──▶ outlook_event_listener
                                     ──▶ outlook_accounts_sender ──▶ outlook_email_sender_service
                ──▶ smtp_accounts    ──▶ smtp_event_listener
                                     ──▶ smtp_accounts_sender ──▶ smtp_email_sender_service
                ──▶ accounts         ──▶ main_api_listener

health back:  accounts_feedback_status ──▶ account_service
```

> **If a mailbox never reaches a listener, that customer simply goes quiet — no
> error surfaces in the send pipeline.**

The `accounts` queue is bound with all four routing keys, so it sees every
mailbox event regardless of provider.

**Mailbox unblocking:** Microsoft restricts mailboxes that trip outbound limits.
`outlook_event_listener` emits `email_status_alerts`;
`restricted_user_unblocker_main_service` (Python) drives the unblock against the
Exchange admin API with certificate-based app auth.

## 4. Inbound capture

Four provider pipelines, same two-stage shape, converging on **one** queue:
`email_status_to_sort`.

```
┌──────────┐  raw message ref  ┌────────────┐  normalised event
│ LISTENER │ ────────────────▶ │ ENRICHMENT │ ────────────────▶ email_status_to_sort
└──────────┘                   └────────────┘
polls the provider,            fetches body, parses headers,
decides what's interesting     threads, replies, matches to a contact
```

| Provider | Listener | Handoff | Enrichment | Stack |
|---|---|---|---|---|
| Gmail | `gmail_event_listener` | `gmail_processor` | `gmail_enrichment` | TypeScript |
| Outlook / M365 | `outlook_event_listener` | `outlook_processor` | `outlook_enrichment` | .NET |
| SMTP / IMAP | `smtp_event_listener` | `smtp_processor` | `smtp_enrichment` (older: `mts_enrichment`) | .NET |
| SendGrid | `sendgrid_webhook_i_v1` / `sendgrid_importer` | `email_events` | `sendgrid_enrichment` | Node |

Gmail is the most developed and the only one with dead-letter queues wired up.
Its listener runs a **2-minute cron** and splits work per mailbox
(`gmail_listener_fetch_messages_per_user`) so one slow mailbox cannot block the
rest. **Gmail API quota** is the hard ceiling: 1.2M quota units/minute per
project, 15k per user; `messages.send` costs 100 units.

**`gmail_processor_event_not_matched`** holds mail that arrived in a connected
mailbox but could not be tied to a known contact or sequence — separate
consumer, so unmatched mail never blocks the main path.

Classification of replies is **regex over the message text**, not AI (see §7):
bounce, automatic-reply, blocked and unsubscribe patterns — the unsubscribe
regex alone carries ~30 hand-collected misspellings.

## 5. Sorting and state machines — the brain

**Sorting** answers *"what kind of message is this?"* **State machines** answer
*"so what happens to this contact?"*

```
email_status_to_sort ──▶ email_sorter ──┬──▶ email_status ──▶ task_service ──▶ sf_exporter ──▶ Salesforce
                                        ├──▶ state_in ──▶ ┌──────────────────┐
                                        │                 │  STATE MACHINES  │ (xstate)
                                        │                 └──────────────────┘
                                        │                        │ state_out
                                        │                        ▼
                                        │        state_machine_processing_i_v1
                                        │           │      │        │        │
                                        │    scheduler_q  email_status  list_service  activity-log
                                        └──▶ create_event_emails ──▶ statistics_service
```

| Service | Entry queue | Role |
|---|---|---|
| `state_machines` | `state_in_alt` | Newest generation |
| `state_machine_service_i_v1` | `state_in` | The long-standing main machine |
| `email_response_state_machine` | `state_in_email_status` | Reply classification outcomes |
| `sequence_state_machine` | `state_in_sequence` | Sequence-level, not contact-level |
| `state_machine_processing_i_v1` | `state_out` | Executes the side effects |
| `state-machine-processing-send-email` | `state_out_send_email` | Turns "send next" into a job |

Four named machines from the design docs: **M1** sequence on/off/archive, **M2**
sequence steps, **M3** thread on/off, **M4** contact added/removed/paused/
finished.

### The one design idea to internalise

**Decision and effect are deliberately split.** A machine consumes `state_in*`,
computes the transition, emits `state_out*` describing *what was decided*. A
separate service consumes `state_out*` and performs the effects.

> **If effects are not happening but state is advancing, the fault is in a
> `state_out` consumer, not in the machine.**

Five entry queues (`state_in`, `state_in_alt`, `state_in_sequence`,
`state_in_email_status`, `state_in_email_response`) feed overlapping services,
and `state_in` is bound to **both** `factur_exchange` and `email_subsystem`.
Trace the specific queue end to end before changing routing.

## 6. Outbound send

```
scheduler_queue ──▶ email_scheduler_service_i_v1   WHO gets WHAT and WHEN
                    (sending windows, timezones, mailbox capacity, stuck retries)
                         │ state_in → machine → state_out_send_email
                         ▼
                    state-machine-processing-send-email
                         │ email_to_process
                         ▼
                    email_processor_service_i_v1    renders the template:
                                                    merge fields, spintax, tracking links,
                                                    unsubscribe, threading headers
                         │ routes by the mailbox's provider
        ┌────────────────┼─────────────────────┐
   email_to_esp   email_to_esp_outlook   email_to_smtp
        │                │                     │
  email_sender_    outlook_email_        smtp_email_
  service_i_v1     sender_service        sender_service
   (Gmail API)      (MS Graph)             (SMTP)
        └────────────────┴─────────────────────┘
                         ▼  email_status + state_out → back to the machines
```

**Three senders, not one with branches**: Gmail (OAuth, `threadId`, daily caps),
Outlook (MSAL against Graph; Microsoft can restrict a mailbox outright), SMTP
(no API-level delivery feedback — events return via the SMTP listener).

`email_scheduler_service_i_v1` is the **busiest service in the platform**. Seven
dedicated queues keep bulk maintenance off the per-contact path: mailbox
capacity rebalance, retry stuck contacts, schedule-on-delivered, sequence
edited / paused / archived, bulk thread updates. Crons at ~2, 5, 15, 25 and 35
minutes plus a daily 04:00 sweep.

**Per-mailbox throttles** are set in the UI: daily limit, hourly limit, minimum
delay between sends, and a per-mailbox signature.

**Schedules** control *when*: named schedules with per-day time windows, a
timezone, an option to use the contact's own timezone, and US national-holiday
skipping (holidays pulled from `date.nager.at`).

**Sequence rulesets** control *whether*: finish a contact on link click, finish
on out-of-office, suppress by contact stage or account stage, CC/BCC addresses,
and a maximum sends per rolling 24 hours. One ruleset is the default.

## 7. AI services — mostly switched off

Two generations, and the older one is **not running**.

| | Self-hosted classification | Hosted generative |
|---|---|---|
| Services | `facture_ai_ingestion` + `facture_ai_email_processing` | `ai_integration_api` |
| Model | Local PyTorch / HuggingFace, checked into the repo | Google Gemini via `@google/genai` |
| Interface | RabbitMQ, async | HTTP (NestJS + Swagger) |
| Vintage | 2023 | 2026 |
| **Status** | **Queues marked "turned off"** | **Live** |

The operational RabbitMQ inventory lists `ais_gmail`, `ais_inbound_tasks`,
`ais_inference`, `ais_inference_status` and `ais_task_status` — the entire 2023
classification chain — as **turned off**, along with `activity-log` and
`activity-log-sequence`. The architecture page separately notes `ais_gmail` and
`ais_task_status` have no consumer in any repository. **Reply classification in
production is regex, not ML.**

`ai_integration_api` is the live AI, and is structurally different: NestJS with
Swagger, JWT/Passport, SpiceDB checks, TypeORM on MySQL. Three capabilities:

1. **Intelligent account search** — natural-language company search ("manufacturing
   companies in US with revenue over $1 million"), the only module using chunked
   processing and DB caching.
2. **Email thread rewriting** — rewrites sequence copy while preserving spintax,
   scores spam risk, flags spam words, sanitises HTML.
3. **Analytics** — logs every AI call: tokens, patterns, success rates.

It holds a **pool of Gemini API keys with round-robin rotation** (thread-safe via
`async-mutex`) to spread load and dodge per-key rate limits; adding a key
increases capacity immediately.

## 8. Salesforce and ZoomInfo

**Inbound:** `salesforce-importer` pulls via jsforce and stages to S3 →
`salesforce_importer_processing` (cron every minute) transforms and dedupes →
`inbound_tasks`, `ais_inbound_tasks`, `sf_datasync`. Which objects sync is
controlled Salesforce-side by a **Custom Metadata Type, `Salesforce Importer
Mapping`** — one record per sObject naming the fields, batch size, export order
and whether child records chain. Leaving the field list empty exports *every*
field.

**Outbound:** three independent producers converge on one consumer.

```
cdc-listener          (MongoDB change streams)  ──┐
task_service          (engagement → SF task)    ──┤──▶ sf_exporter ──▶ salesforce_exporter ──▶ Salesforce
salesforse-datasync   (reconciliation, every 5s)──┘
```

- **CDC instead of dual writes.** `cdc-listener` tails MongoDB change streams
  rather than making every writer notify Salesforce — **so an unintended write
  propagates straight into the customer's CRM.**
- **`sf_exporter` is a convergence point** for three producers on very different
  cadences. **If Salesforce writes look duplicated, look here first.**

A NestJS rewrite of the exporter is planned: REST *and* Bulk APIs chosen by
strategy, a metadata-driven mapping layer so only valid fields go out, Mongo-side
validation before export, and a review of existing Salesforce triggers/flows to
avoid recursive updates.

**ZoomInfo:** search via the standard API (100/page), then enrichment in batches
of 25, capped at 10,000 contacts per filter, matched on `personId`, results
written through `account_contact_sync_service`. Bulk reconciliation via
`zoominfo_datasync`. Credentials from AWS Secrets Manager.

## 9. Deliverability — the sharpest document in the space

`deliverability_service` (NestJS 11) answers one question per sending domain and
mailbox: **why is our mail not landing?** Every figure in its documentation was
measured against live production data, and it is worth reading in full.

| Channel | Source | Size | Measured failure rate |
|---|---|---|---|
| Gmail | `gmail_event_enrichment.messages_active_latest_v3` | 47.3M rows / 636 GB | ~12% |
| Outlook | `outlook_event_enrichment.email_messages` | 129.3M rows / 404 GB | ~23% |
| SMTP | `smtp_event_enrichment.email_messages` | 2.0M rows / 3.3 GB | — |

**Outlook is the bigger and worse channel** — more rows than Gmail and roughly
twice the bounce rate. A Gmail-only view reports on the healthier half while
looking complete, which is what the first version did.

### What the failure data actually says

Gmail failures (8,000 live reports): **list-quality 52.5%**, infra/not
attributable 32.2%, **reputation 14.8%**, transient 0.5%.
Outlook (5,000 reports): **list-quality 79.2%**, reputation 15.1%.

> A single bounce rate conceals this, and the two dominant causes need opposite
> responses. Pausing a mailbox does nothing for bad recipient data; cleaning a
> list does nothing for a Spamhaus listing.

**112 distinct sending domains** were named explicitly by Spamhaus DBL in
provider rejection text in one sample window, clustering into lookalike families
sharing one human sender. Domain rotation of that shape is exactly what Spamhaus
DBL is built to detect — each new lookalike inherits its siblings' reputation, so
**adding domains accelerates the problem rather than routing around it.** The
document calls this a strategy-level finding the service cannot fix.

### Traps it documents (each produced wrong numbers first)

- The RFC 3464 `delivery-status` node carries no data of its own — the fields sit
  in a `text/plain` child. Reading the node's own body parsed **0 of 6,000**.
- Never pattern-match the whole document: the forwarded original carries
  `Received-SPF` / `DKIM-Signature` on every send, so matching `/spf|dkim/` across
  it reported auth failure on **81% of bounces, none real**.
- **Attribution flips by row type.** On a send, our mailbox is `emailFrom`; on any
  response row it is `emailTo` (a bounce's `emailFrom` is `mailer-daemon@…`).
  **Any metric grouping by `emailFrom` alone credits every failure to the remote
  reporter and leaves our domains looking spotless.**
- **Deferrals are not blocks.** ~22% of what is reported as `spam_block` is a
  4.x.x "please retry", so the headline 12.2% block rate materially overstates
  real blocking.
- Spamhaus answers `127.255.255.252` for *query refused — open resolver or over
  free limit*. Treating any A record as a hit reports the whole estate as
  blocklisted; treating it as no-answer reports it all clean. With ~6,600 sending
  mailboxes a **Data Feed Query Service subscription and dedicated resolver are
  required**; without one, probing is skipped rather than reporting untrustworthy
  results.
- A throughput defect: the first version processed 192,000 ids/day against 14.4M
  ingested — **75x too slow**, and it reported success every run. Fixed by
  aggregating sends server-side (167 ms vs 16.9 s for the same range) and
  fetching only failure bodies.

**Invalidation** (marking a sender invalid in Mongo) fires on a blocklist
listing, never on list-quality failures however high — "at 52.5% of Gmail
failures and 79.2% of Outlook failures, a naive high-bounce-rate rule would
disable most of the estate for a problem living in the contact list."

**Open items:** the target Mongo collection is unknown and deliberately has no
default; SendGrid has no extractor; `policy-other` absorbs 25% of Gmail reports;
and a content scan of **254,306 sequence threads found 80.9% with no unsubscribe
mechanism**, 46% using synthetic `Re:` threading, 59% spintax, 1.9% containing
links. Collected but not yet scored.

## 10. Messaging and reliability

RabbitMQ (AmazonMQ). All exchanges **direct**; convention is **routing key =
destination queue name**. Main bus `factur_exchange` with `factur_exchange_dlx`
for dead letters, plus `accounts_subsystem`, `clients_subsystem`,
`gmail_listener_subsystem`, `outlook_subsystem`, `smtp_subsystem`,
`email_subsystem`, `email_status`, `state_machine_subsystem`, `ai_subsytem`,
`sf_import` / `sf_export`.

### ⚠️ Misspelled exchange names are live and load-bearing

Several exchanges exist in **both** a correct and a misspelled form, and **both
are live in the broker**. Different services bind to different spellings.

| Correct | Misspelled | Notes |
|---|---|---|
| `email_subsystem` | `email_subsytem` | `sendgrid_importer`, `sendgrid_enrichment`, `gmail_enrichment_v1` use the misspelling; `email_sorter` and `sendgrid_enrichment_i_v1` the correct one |
| `state_machine_subsystem` | `state_machine_subsytem` | |
| — | `ai_subsytem` | Misspelling only, but **consistent everywhere**, so it works |

**This is a real source of "the message vanished" bugs.** Check the spelling
before concluding a message was lost, and never "correct" one service alone.
Also: `sf_exporter` is used as both a queue *and* an exchange name, alongside the
real `sf_export`; the repo is spelled `salesforse-datasync`; and the deployed
environment is `outlook-event-lisntener`.

### messaging-lib is where reliability lives

`@facturgit/messaging-lib` provides retry with dead-lettering (`<queue>_retry`
with TTL, then `<queue>_dlq` after `RABBIT_MAX_RETRIES`), consistent-hash
exchanges (all messages for one mailbox or contact land on the same consumer, in
order, while still scaling out), graceful shutdown draining in-flight messages,
and automatic reconnection.

> **The `*_i_v1` family predates this library and each hand-rolls its own AMQP
> client with none of the above. That is the single biggest reliability
> difference between the old and new generations of service.**

RabbitMQ has crashed under connection exhaustion before (2023-09-20), traced to
multithreading opening 3 connections per .NET service instance.

## 12. The public database — a separate product

`data.facturmfg.com` is a **read-only public company-search site** with ~9
million accounts, deliberately isolated from the CRM: its own VPC, its own
DocumentDB cluster, its own Elastic Beanstalk application, AWS account
231649199813.

| Layer | Tech | Where |
|---|---|---|
| Frontend | **Angular 19 SSR** (standalone components + signals, no NgModules, no NgRx), Node 22 | EB `fp-website-frontend`, `data.facturmfg.com` |
| Backend | Plain JS, **Express 4**, Node 24, MongoDB native driver (no Mongoose) | EB `fp-website-backend`, `api.facturmfg.com` |
| Database | **DocumentDB 5.0**, cluster `fp-website`, db `accounts` (~9M docs) | Private subnets, VPC only |

SEO-critical pages (company, industry, location) render server-side;
`/search` renders client-side only. Anti-scraping via helmet, rate limiting,
speed bumps, a bot User-Agent check, and Cloudflare Turnstile. Results capped at
1,000 per search. Only an allow-listed field set ever leaves the database —
hygiene flags (`IsDuplicate`, `IsDeleted`, quality tier) are used for filtering
and never returned.

**Resilience gaps its own docs flag:** both EB environments run min=max=1, so
each is a single point of failure; DocumentDB is a single instance, not Multi-AZ;
backups retained 3 days. Facets were reduced to four fields for memory, and
`DISABLE_FACETS` is currently `TRUE` in production. Several indexes may be
missing because the live collection was loaded outside the import scripts — the
stated primary cause of slow filtered searches.

**Gotcha worth keeping:** the live database is named `accounts`, not `factur`. A
wrong DB name returns 0 documents rather than erroring, which previously
masqueraded as a filter bug.

## 13. Network architecture

Main platform VPC `factur-develop` (`10.0.0.0/16`), us-east-1, three AZs, three
public `/20` and three private `/20` subnets. Internet Gateway for public;
**single zonal NAT Gateway** in us-east-1b for private egress — its own docs note
that AWS best practice is one per AZ and that an AZ failure would cut outbound
access. VPC endpoint for AWS services. Bastion host for SSH; no public database
endpoints.

DNS in Route 53 across `fixtur.io`, `factur-aws.com` and `unsubdom.com` (the
email-event receiver domain), each with a public and a private hosted zone.
Frontend via CloudFront; internal services resolve only inside the VPC.

## 14. Security — act on these

**1. Plaintext credentials in Confluence.** The page **"Accounts" (id 5701646)**
opens with *"DO NOT SHARE THIS PAGE WITH ANYONE"* and lists **live usernames and
passwords** — Apollo, the dev app at `app.fixtur.io`, Swagger, and several
application users. Rotate everything on it; **delete the page including version
history** (an edit leaves old versions readable); move to AWS Secrets Manager;
audit who can read the space.

**2. SSH open to the entire internet.** The security-group inventory (134 groups)
shows **`tcp 22: 0.0.0.0/0` on a large number of Elastic Beanstalk instance
groups**. This directly contradicts the Bastion page, which states
"Unrestricted SSH access (0.0.0.0/0) is not permitted." Also exposed to
`0.0.0.0/0`: **`tcp 50051`** (gRPC — SpiceDB's port, i.e. the authorization
service), **`tcp 9100`** (Prometheus node exporter), and `tcp 3000` (Grafana).
The `factur-develop-pmm` group opens 22, 80 and 443 to the world.

**3. Committed `.env` files.** Factur's own code sweep found several repositories
containing `.env` files with a **live message-broker connection string including
its password.**

**4. Monitoring on plain HTTP at a public IP.** `log-metric-viewer.fixtur.io` →
`http://54.85.242.224:3000`, the Grafana/Loki dashboard, over HTTP.

**5. Compliance exposure.** 80.9% of 254,306 sequence threads carry **no
unsubscribe mechanism**, and 46% use synthetic `Re:` threading. Under CAN-SPAM
that is a per-message liability, quite apart from what it does to deliverability.

## 15. Things to be careful about

- **Duplicated service generations run side by side** and it is not obvious which
  is authoritative: `state_machines` vs `state_machine_service_i_v1`,
  `email_sorter` vs `email_event_sorter_i_v1`, `sendgrid_enrichment` vs
  `sendgrid_enrichment_i_v1`, `smtp_enrichment` vs `mts_enrichment`,
  `gmail_enrichment` vs `gmail_enrichment_v1`, `csv_export` vs
  `contact_export_service_i_v1`, `cron_service_i_v1` vs
  `data_cleanup_cron_service`.
- **`cron_service_i_v1` and `data_cleanup_cron_service` are near-identical
  forks** — both report `name: facture_cron`, ~100 shared files. A change to one
  is easy to forget in the other.
- **Two API generations coexist:** `main_api_backend_v1` (Express monolith,
  ~340 files, the only service touching all six data stores) and
  `main_api_rework` (NestJS rewrite), with `main_api_sidecart` for authorization.
- **`state_out_send_email` vs `state_out_send_email_new`** — both routing keys
  bind to the same queue. A migration artefact, not two paths.
- **`deliverability_service` may overlap `domain-status-service`** — its own docs
  say reconcile scope before deploying both.
- **`analytics-service` and `shared_libraries` are empty repositories.**
